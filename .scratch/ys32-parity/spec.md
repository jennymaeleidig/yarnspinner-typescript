# Yarn Spinner 3.2 parity

Label: ready-for-agent

## Problem Statement

The library is a TypeScript reimplementation of Yarn Spinner, but it has drifted from the real thing: content written for live Yarn Spinner 3.2.2 fails to compile, compiles but behaves differently, or uses fork-only syntax that upstream would reject. The runtime API is a one-method `advance()` loop that cannot express upstream contracts (option fall-through, line hints, node lifecycle, pluggable variable storage), there is no localisation support, no usable diagnostics, no saliency machinery, and the once-state bug leaks across runner instances. Maintainers cannot even verify parity, because nothing tests this implementation against upstream's own conformance corpus.

## Solution

Bring the parser, compiler, and runtime to full language-and-behavior parity with Yarn Spinner 3.2.2: any `.yarn` script that compiles upstream compiles here with the same diagnostics, and runs here with the same observable behavior. The public API is reshaped to the shape both official implementations converge on — a compile pipeline producing a program, string table, and collected diagnostics, and a pull-based runtime emitting a stream of dialogue events with pluggable variable storage, a function/command library, and an injectable text provider. Parity is continuously proven by running upstream's own test corpus as golden conformance tests. Nonstandard fork syntax that collides with upstream is removed; the React adapter survives untouched except for migrating to the new runtime API so the browser demo stays green.

## User Stories

1. As a dialogue author writing Yarn Spinner 3.2 content, I want my `.yarn` scripts to compile in TypeScript exactly as they do upstream, so that I can share scripts between projects without edits.
2. As a dialogue author, I want line-level `<<if>>`, `<<once>>`, and `<<once if>>` conditions, so that I can gate individual lines the way upstream content does.
3. As a dialogue author, I want compound assignment in `<<set>>` (`+=`, `-=`, `*=`, `/=`, `%=`), so that I can write idiomatic 3.x arithmetic.
4. As a dialogue author, I want a `<<call>>` statement, so that I can invoke functions as explicit statements.
5. As a dialogue author, I want `<<return>>` to end a detour (and act as stop outside one), so that detour-based flows behave as upstream.
6. As a dialogue author, I want `<<jump>>` inside a detoured node to clear the return stack, so that control flow matches upstream semantics exactly.
7. As a dialogue author, I want built-in `<<wait>>` delivered as a consumer-timed command, so that I can pause dialogue for a duration in my host.
8. As a dialogue author, I want `<<stop>>` to actually halt dialogue and fire the dialogue-complete event, so that ending a conversation works.
9. As a dialogue author, I want to escape `:` in character names, so that I can write names like `Scene 2\: The Reveal`.
10. As a dialogue author, I want `<<set>>` to require the `$` prefix, so that my scripts are valid upstream content and bare variables are caught with a clear diagnostic.
11. As a dialogue author, I want full enum declarations with uniform raw values and auto-numbering, so that my enums round-trip with upstream projects.
12. As a dialogue author, I want `.Case` shorthand and same-enum-only `==`/`!=` comparisons, so that enum logic reads the way upstream scripts do.
13. As a dialogue author, I want smart variables that are read-only and recomputed on every access, so that derived state like `$gold = $coins * 2` always reflects current values.
14. As a library consumer, I want to register host-defined enums from TypeScript (the EnumTypeBuilder equivalent), so that my code-side enums participate in compile-time checking and `.Case` expressions without declaring them in `.yarn`.
15. As a dialogue author, I want self/cyclic smart-variable references to be compile errors, so that I don't ship infinite evaluation loops.
16. As a dialogue author, I want `<<declare $var = value as Type>>`, so that my variable types are validated at compile time.
17. As a dialogue author, I want node groups with `when:` headers evaluated by real saliency (complexity scoring and all four strategies, Random Best-Least-Recently-Viewed by default), so that storylet-style content selects content the way upstream games do.
18. As a dialogue author, I want `<<set_saliency>>`, so that I can change selection strategy mid-story.
19. As a dialogue author, I want line groups `=>` with conditions and `once`, so that I can offer alternative phrasings selected by saliency.
20. As a dialogue author, I want `has_any_content()` and runtime queries for node groups, so that my UI can check whether a group still has anything to say.
21. As a dialogue author, I want a compile error when a node-group member lacks a `when:` header, so that group mistakes surface at build time.
22. As a dialogue author, I want the `tracking: always|never` header, so that I can force or suppress visit tracking per node.
23. As a dialogue author, I want `visited()` and `visited_count()` to report on node return and aggregate node-group visits under the shared title, so that visit-based logic matches upstream.
24. As a dialogue author, I want `subtitle` headers supported (with duplicate detection inside node groups), so that internal node names survive round-trips.
25. As a dialogue author, I want shortcut options with `<<if>>` conditions and `<<once>>`, so that my option lists behave exactly like upstream scripts.
26. As a dialogue author, I want all upstream markup parsing features — close-all `[/]`, property shorthand, self-closing whitespace-trim, attribute types — so that annotated text parses identically.
27. As a dialogue author, I want `[select]`, `[plural]`, and `[ordinal]` replacement markers, so that my text adapts to values and locales the way upstream text does.
28. As a dialogue author, I want character-name prefixes to become implicit `[character name=]` markup, so that speaker identity is structured data rather than a stripped string.
29. As a dialogue author, I want the `#shadow:` mechanism with compile-time validation, so that shadow lines reuse text without breaking string tables.
30. As a dialogue author, I want hashtags on lines and options to carry values, so that metadata survives to the runtime.
31. As a library consumer, I want `compile()` to accept multiple files and return a program, string table, declarations, and collected diagnostics, so that I can build multi-file projects.
32. As a library consumer, I want external declarations (variables, functions, enums) provided by my code, so that the type checker knows about host-side state.
33. As a library consumer, I want compilation modes (full, strings-only, declarations-only, type-check-only), so that I can power linters and string-table tooling without full compiles.
34. As a library consumer, I want diagnostics collected by default with code, severity, message, file, and range, so that I can surface all problems at once in my tooling.
35. As a library consumer, I want an optional strict mode that throws on the first error, so that fail-fast builds stay simple.
36. As a library consumer, I want diagnostics aligned with upstream's stable YS-code registry, so that I can look up any diagnostic upstream and get the same meaning.
37. As a library consumer, I want a pull-based runtime where `continue()` returns the events up to the next stopping point, so that I drive dialogue on my own clock without callback spaghetti.
38. As a library consumer, I want events for lines, options, commands, node start/complete, dialogue complete, and opt-in line hints, so that I can react to the full dialogue lifecycle.
39. As a library consumer, I want a pluggable variable storage interface with an in-memory default, so that I can persist dialogue state wherever I want.
40. As a library consumer, I want `selectOption()` with a no-option-selected fall-through, so that all-options-unavailable situations fall through to post-option content like upstream 3.1.
41. As a library consumer, I want a Library registry for variadic functions and command handlers, so that hosting custom behavior is one registration, not constructor plumbing.
42. As a library consumer, I want once-state, visit state, and saliency history stored as generated variables in variable storage, so that resetting storage resets all story state together and multiple runtimes never share state.
43. As a library consumer, I want an injectable text provider with language switching, so that I can resolve line text per locale without the runtime knowing about tables.
44. As a library consumer, I want a CSV-backed translation provider shipping out of the box, so that localisation works end-to-end on day one.
45. As a localizer, I want string-table CSV export in the upstream 8-column format with lock hashes, so that my translation pipeline treats this project's output as upstream-compatible.
46. As a localizer, I want implicit line IDs generated with the upstream CRC32 scheme (or pluggable generators including random and descriptive taggers), so that line IDs are stable and upstream-tool-compatible.
47. As a localizer, I want `///` declaration comments supported per upstream 3.x semantics, so that my documentation tooling behaves the same.
48. As a tooling author, I want the compiled program as versioned JSON, so that I can inspect, diff, and pre-compile programs without protobuf tooling.
49. As a maintainer, I want the conformance suite to run upstream's own fixture corpus as golden tests, so that parity regressions are caught by the same tests upstream uses.
50. As a maintainer, I want once-state fixed to be per-runtime (via generated variables), so that two runners in one process can't corrupt each other's story state.
51. As a maintainer, I want the compiler to validate jump targets and duplicate titles/subtitles with proper YS codes, so that whole classes of silent bugs become build errors.
52. As a maintainer, I want expressions compiled to bytecode instead of re-evaluated from strings at runtime, so that evaluation is fast, typed, and diagnosable.
53. As a maintainer, I want the browser demo migrated to the new runtime API and kept green, so that the demo remains the fastest way to see the library work.
54. As a maintainer, I want the docs rewritten to match reality (removing the stale compatibility checklist, the nonexistent ternary, and `&css{}`), so that contributors aren't misled.
55. As a demo user, I want the browser demo to exercise node-group saliency and strategy switching, so that I can see the new machinery working.
56. As a TypeScript developer evaluating this library, I want behavior parity with upstream 3.2.2 as the contract, so that any upstream tutorial or content works unmodified.

## Implementation Decisions

These decisions were made in the wayfinding effort ([map](map.md), tickets 01–16) and are binding for the spec:

- **Parity contract**: language + behavior parity with Yarn Spinner **3.2.2**. A 3.2 script compiles with the same diagnostics and runs with the same observable behavior. No protobuf `Program` artifact compatibility.
- **Syntax removals** (breaking, intentional): option-condition `[if expr]` suffix dropped outright (upstream `<<if expr>>` on the option line is the only syntax); inline `{if}{else}{endif}` text blocks dropped (collides with `{expr}` interpolation); `&css{}` removed from core (styling is consumer-side via markup properties). Migration notes in the spec's release notes.
- **Syntax additions**: line-level `<<if>>`/`<<once>>`/`<<once if>>`; `<<call>>`; compound assignment; `<<return>>` + detour/jump interaction; built-in `<<wait>>` (consumer-timed command) and working `<<stop>>`; escapable `:`; `subtitle` header (with YS0032-style duplicate check); `$`-prefix strictness with a diagnostic for bare variables; full enums (uniform raw values, auto-numbering, `.Case`, same-enum comparison restriction); full smart variables (read-only, recompute-on-access, cycle detection).
- **Runtime API (breaking reshape)**: Rust-style pull model — `continue() → DialogueEvent[]`. Event set: `Line`, `Options`, `Command`, `NodeStart`, `NodeComplete`, opt-in `LineHints`, `DialogueComplete` (camelCased). State commands (`<<set>>`/`<<declare>>`) are internal and never surface as `Command` events (ticket 03 conformance); runtime diagnostics surface as `logError`/`logDebug` option callbacks — diagnostics, not dialogue events (ticket 10). `advance()` is removed; replaced by `continue()`, `selectOption(index | noOptionSelected)` (the TS parameter value rendering upstream's `NoOptionSelected` concept), `setNode(title)`, `stop()`. The no-option-selected fall-through is adopted (3.1 conformance).
- **State model**: pluggable variable storage (bool/number/string) with an in-memory default; once-state, visit tracking, and saliency history all live as generated variables in storage (upstream mechanism) — fixing the global once-state bug; visits recorded on node return; `tracking: never` suppresses recording, `tracking: always` equals default behavior; node-group visits aggregate under the shared title.
- **Runtime evaluation adaptation (pre-diagnostics)**: comparing against an unset variable uses the implicit type default inferred from the comparison's other side (bool→false, number→0, string→""). Upstream compile-errors on undefined variables; until the diagnostics channel exists (phase 1), a comparison must not crash the run, so the evaluator substitutes the default. Narrow scope: reads, not writes; the `<<declare>>`-seeding of initial values (upstream `Program.InitialValues`) removes most real uses. Recorded with ticket 01's review follow-ups.
- **Registration**: a Library-style registry for variadic functions and command handlers replaces the constructor `functions` map / `handleCommand` split. Built-ins conform: `random_range` returns int, min/max/floor family variadic-or-correct-arity, `has_any_content` and `format` added.
- **Saliency**: full machinery — complexity scoring (`always`=0, `once`+1, expression = boolean-operator count +1), four strategies (First, Best, Best-Least-Recently-Viewed, Random BLRV default), pluggable two-method strategy interface, `<<set_saliency>>` command, node-group conformance errors, and query APIs (`isNodeGroup`, saliency options, `hasSalientContent`).
- **Markup**: upstream split adopted — the compiler stores raw line text; a runtime line-parser module expands `{expr}` substitutions then parses markup into a structured parse result (attributes with positions, delete-range, text-for-attribute). Replacement markers `[select]`/`[plural]`/`[ordinal]` implemented via `Intl.PluralRules` with overridable locale, plus invisible-character counts. Parser completeness: close-all `[/]`, property shorthand, self-closing whitespace-trim with `trimwhitespace=false`, attribute types. Implicit `[character name=]` marker generated first, replacing the regex speaker slice. A minimal custom-processor registry (name → processor) sits alongside the built-in markers. Styling tags remain opaque data for the consumer.
- **Compiler**: `compile(files: CompileFile[])` with `{ name, source }` entries — no globs or filesystem I/O inside the library. External declarations API (variables/functions/enums) feeding the type checker; in-script `<<declare>>` conflicts produce YS-table diagnostics. **Host-defined enums are in scope** (the EnumTypeBuilder equivalent): hosts register enum types from TypeScript, which flow through the external declarations path into compile-time checking, `.Case` resolution, and `userDefinedTypes` — the same relationship upstream's `EnumTypeBuilder` output has to `CompilationJob.Declarations`. Four compilation modes: full, strings-only, declarations-only, type-check-only (which also emits the string table). A Library accepted at compile time for signature checking (variadic arity); the runtime keeps its own instance. Result shape mirrors upstream camelCased: `{ program, string table, declarations, diagnostics, file tags, implicit-string-tag flag, user-defined types }`.
- **IR/VM**: the tree-shaped IR retires. The compiler emits a **TS-idiomatic instruction-stream stack VM program** with upstream-equivalent observable semantics; the AST remains the front-end representation. Expressions compile to bytecode (the current string evaluator becomes the compiler's expression codegen). Program format: versioned JSON with a `languageVersion` field. Jumps are instruction indices (labels resolved in a compiler pass). VM machinery per prior decisions: per-node line-ID table for opt-in `LineHints`, dedicated saliency-candidate ops, detour/return as a call stack of return addresses (jump inside detour clears it), generated variables for state.
- **Diagnostics**: collect by default (compile continues), optional strict flag throws on first error. Diagnostic shape: `{ code, severity, message, file, range, context }` (upstream `Diagnostic` adopted; fixes missing line/column). First-spec target: the ~22 adoptable YS-codes from the catalog, explicitly including the diagnostic-shape code, smart-variable read-only, jump-target validation, duplicate detection, duplicate subtitle, smart-variable cycles, the type-error catch-all, and markup diagnostics folding into compilation. The 3.2.2 per-code markdown registry in the upstream repo is authoritative (the docs page is stale on severities; YS0001/YS0002 are deprecated dead codes — live type errors use the catch-all code).
- **Localisation**: full compiler layer — implicit line IDs via upstream CRC32(file+node+count) (replacing the fork's global counter), explicit `#line:` verbatim, `#shadow:` compile-time validation, string table as compile output. CSV strings files in the upstream 8-column format (`language,id,text,file,node,lineNumber,lock,comment`; `lock` = first 8 hex of SHA-256 of base text; `comment` = line hashtag metadata — `///` comments attach to declarations only in 3.x). Pluggable line-tag generator seam with random (default) and descriptive built-ins, plus the `tagLines(source, { generator })` source-rewriting utility (ticket 11's recommendation, adopted). No `.yarnproject` equivalent. A CSV-backed runtime translation provider ships at launch (`setLanguage`) over the injectable text-provider seam.
- **React adapter**: out of the parity scope; migrated in the final phase to the new runtime API so the browser demo stays green, plus a node-group/saliency storylet demo exercising strategy switching.
- **Docs**: rewritten to match reality — stale compatibility checklist removed/replaced, ternary claim deleted, removed-extensions documented as migration notes.

## Testing Decisions

- **Behavior over internals**: tests assert only public observable behavior — compiled outputs (program, string table, declarations, diagnostics) and runtime event streams — never VM internals, opcode layout, or private module structure.
- **Seam 1 (primary): the compile → run pipeline.** `compile()` in, `Dialogue` events out. The vendored upstream conformance corpus drives only this seam: the `.testplan` DSL asserts strict event streams (lines with composed text, options with availability, commands, node events, saliency selections, `select: 0` fall-through, `set:` initial values via program initial values) and the ParseFailures files assert expected diagnostic codes. Line IDs, the string table, shadow lines, and diagnostics are observable via the compile output; the multi-file surface (story 31) is exercised by the upstream `Tests/Projects/Basic` and `Space` projects (`.ysls` definitions included) and the `Duplicates/` fixtures. Once-state, visit tracking, `tracking:`, and saliency are observable in the event stream.
- **Seam 2 (narrow): the runtime line-parser module.** The fixture corpus has no markup coverage (an inventoried fact), so the upstream inline compiler/runtime tests for markup are ported to call this module directly: substitutions, markup parse results, replacement markers, plural/ordinal classes via `Intl.PluralRules`, invisible-character counts.
- **Harness provenance**: vendor upstream's `Tests/` corpus at tag 3.2.2 (~40 KB); write a small testplan DSL parser for the current grammar (do **not** port the Rust reader — it parses an obsolete pre-backtick format); port the upstream TestBase event-stream step-lock runner. Harness-registered functions (`assert`, `dummy_*`, `add_three_operands`, quest stubs) are part of the conformance contract and are ported. The upstream culture-independence loop (14 cultures) is ported as an invariant-number-formatting check. CSV/string-table and line-tag-generator behavior has no fixture coverage — ported inline upstream tests cover it (alongside the markup tests) through the compile output and the tagLines utility. Nothing requires Unity; upgrader tests are out of scope (3.x only). `RandomOptions.yarn` is a dead fixture — skipped.
- **Adoption phasing**: (1) vendor + ParseFailures must-fail loop, (2) testplan parser + runner over the 32 pairs, (3) diagnostic-definition examples asserting exact YSxxxx codes.
- **Prior art**: the repo's existing `node --test` suite (46 cases) is the runner precedent; its cases are ported to the new public API during the migration phase. The upstream Rust repo proves the submodule/vendor + ported-TestBase pattern.
- **Acceptance bar**: full fixture pass (phase-2 exit: testplan runner green on the 32 pairs; phase-1 exit: all 32 fixture `.yarn` files compile with expected diagnostics), plus the ported markup tests, plus the migrated demo and existing suite green.

## Out of Scope

- **Protobuf `Program` artifact compatibility** — loading Unity-compiled programs (the JSON program format is this project's own).
- **`.yarnproject` project files** — host-tooling territory; a program + string-table compile API suffices.
- **Unity engine-side features** — MarkupPalette, pause/wave event processors, sfx/colour commands, prefab equivalents.
- **React adapter feature work** — only the migration needed to keep the demo green; the scene/actor system stays as-is.
- **Host-defined enums** are IN scope (amended): register enum types from TypeScript via the external declarations path.
- **Upgrader/legacy Yarn 2.x content** — 3.x only.
- **Removing React from the published package** — the adapter stays; only the phase-4 migration is in scope.
- **Upgrader/legacy Yarn 2.x content** — 3.x only.
- **Writing the implementation** — this spec defines it; the phased roadmap (conformance foundation → compiler & language core → runtime & VM → compiler surface & localisation → migration & ship) prescribes the order.

## Further Notes

- **Version re-check**: before implementation planning, re-check upstream for point releases >3.2.2 and record the exact targeted version in the release notes.
- **Release**: breaking changes land together in one 0.2.0 "3.2 parity" release — no staged deprecation windows, no external consumers to grandfather.
- **Folklore corrections** the implementer should not re-learn the hard way: upstream has no `<<visit>>` and no `<<unset>>` statements (visit state is queried via functions; variables cannot be unset); upstream has no ternary operator; the authoritative YS-code registry is per-code markdown in the upstream repo, not the docs errors page, and extends past YS0047; implicit line IDs are CRC32-based, not counter-based; the CSV `comment` column is hashtag metadata, not `///` doc comments.
- **Research provenance**: every decision above traces to a resolved ticket in [issues/](issues/) with primary-source findings in [research/](research/) (repo audit, 3.2.2 census, diagnostics catalog, Rust reference study, localisation mechanics, upstream fixtures inventory).
- **Phasing**: the five-phase roadmap in the roadmap ticket (conformance foundation → compiler & language core → runtime & VM → compiler surface & localisation → migration & ship) is the prescribed implementation order, with per-phase exit criteria from the fixture corpus.
