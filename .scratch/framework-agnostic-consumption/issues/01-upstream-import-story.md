# Ticket 01 — Upstream reference: how Yarn Spinner itself handles .yarn/.yarnproject import

Type: research
Status: resolved

## Question

How does upstream Yarn Spinner handle importing `.yarn` and `.yarnproject` content, and what can this project's direct-import design mirror or deliberately diverge from? Investigate upstream's Unity asset importer (YarnProjectImporter / `.yarnproject` → Unity asset pipeline), its YarnProject file format semantics (v4 schema: sources, localisation, baseLanguage, compilerOptions), and any tooling (CLI, docs) that compiles `.yarn` files ahead of runtime. Deliverable: a research note in this repo (follow the `research` skill — primary sources: upstream GitHub repo `YarnSpinnerTool/YarnSpinner` and `YarnSpinner-Console`, official docs), cited, saved under `.scratch/framework-agnostic-consumption/research/01-upstream-import-story.md`, framing what the Vite plugin's semantics should inherit from upstream (compile-at-import, diagnostics surfacing, localisation handling) vs what is Unity-specific and must not leak into a web bundler design.

## Answer

Resolved — see [`research/01-upstream-import-story.md`](../research/01-upstream-import-story.md) (primary sources: `YarnSpinnerTool/YarnSpinner`, `YarnSpinner-Unity`, `YarnSpinner-Console`, `YarnProject.schema.json`, docs.yarnspinner.dev).

Short version: upstream's Unity path is a `ScriptedImporter` on `.yarnproject` that parses the project file, resolves `sourceFiles` globs, and compiles the whole project at import time into an embedded Protobuf program asset, with per-file diagnostics; the v4 `.yarnproject` schema (required `projectFileVersion` ≤ 4, `sourceFiles`/`excludeFiles` globs rooted at the project dir, `baseLanguage`, `localisation` map of strings-CSV + assets dir, string-or-list `definitions`, open `compilerOptions` bag) is defined in the engine-agnostic core repo. A non-Unity AOT path exists: `ysc compile` accepts a `.yarnproject` or bare `.yarn` files and emits program + string/metadata CSVs (or JSON on stdout); `ysc list-sources` is the citable glob-resolution reference. The web-bundler plugin should inherit compile-at-import, core project-file parsing semantics, `LanguageVersion` plumbing, localisation-map handling, an external-declarations seam, per-file diagnostic grouping, and inspectable source resolution; Unity-specific mechanisms (GUIDs/asset wrappers, `unity:` external-localisation convention, Unity Localization/Addressables, C# variable codegen, reflection-based action registration, Protobuf output, trailing-`~` excludes) must not leak. Two deliberate divergences flagged for ticket 03: fail-the-build on errors (Unity's always-emit-asset rule is reference-stability-specific) and HMR, for which upstream has no analogue (its recompile-on-change comes from the AssetDatabase).
